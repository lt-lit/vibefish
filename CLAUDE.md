# Vibefish — Claude Code context

Read `DESIGN.md` first. This file is the short version plus hard constraints.

## What this repo is
Commander deck playtesting engine built on Forge's headless `sim` mode. Engine only — decks, playbooks and results live in a separate data repo and are passed in by path. `demo-data/` holds the public pod results the dashboard shows.

## Hard constraints
- **Dashboard:** vanilla JS, no build step, no TypeScript, no frameworks. Must work on GitHub Pages and on a phone browser. It reads only the data contract in `DESIGN.md` §6 (`index.json`, `rollup.json`, `cards/scryfall-cache.json`, and the optional `bots.json`).
- **Images:** never commit card image files. Hotlink `cards.scryfall.io` URLs from the cache only; `small` and `normal` only, never cropped art.
- **Scryfall API:** ≥100 ms between requests to `api.scryfall.com`; set `User-Agent: Vibefish/<version>` in scripts (`runner/scryfall.py` does); leave browser UA alone in page JS. Resolve names in batches via `cards/collection`.
- **Forge:** pinned to the tag in `forge/VERSION` with the checksum in `forge/SHA256SUMS`. Do not float to `latest` or `daily-snapshots` unless `FORGE_CHANNEL=snapshot` is explicitly set; a snapshot build that published runs depend on is pinned exactly with `FORGE_SNAPSHOT_BUILD=<build>` and its checksum recorded in `forge/SHA256SUMS` (the 2026-11-08 and 2026-11-10 builds are). The runtime is downloaded by `forge/fetch-forge.sh` into `forge/runtime/` and is never committed. Forge's `daily-snapshots` release holds one tarball at a time, so a pinned snapshot can be fetched from upstream only until the next snapshot replaces it (checked 2026-11-11 16:16 UTC: the 11-10 tarball was still there, no 11-11 build yet, 11-08 and 11-09 answered 404). Snapshot builds that published runs depend on are therefore archived (decided 2026-11-11): `forge-archive.yml`, started by `runner/queue/forge-archive.json`, packs the assembled runtime and attaches it to this repository's release `forge-runtimes`; `forge/SHA256SUMS` lists the archive (`forge-runtime-snapshot-YYYY-MM-DD.tar.gz`), and `forge/fetch-forge.sh` fetches a pinned `FORGE_SNAPSHOT_BUILD` from there when it is listed. The 11-08 and 11-10 builds are archived. When a new snapshot is first used for a published run, archive it straight away (while upstream still has it or the Actions cache does) and add the checksum it prints. The Actions cache key hashes `forge/VERSION`, `forge/SHA256SUMS` and `forge/fetch-forge.sh`, so editing them makes the next run fetch again: fine for archived builds, fatal for a snapshot that is not archived yet. The archive is for reproducing published runs, not for staying on old builds: keep up with Forge (the 2.0.16 release came out on 2026-11-11 and the pin has not moved yet: Status, Next, the Forge item).
- **No Forge fork.** `controller/` compiles against the released Forge jar and uses public hooks (event bus, `PlayerControllerAi`). Patch Forge only if a hook is private, and record it in `DESIGN.md`.
- **No contact with anyone** (the owner, 2026-11-11, in so many words): the owner writes to nobody, posts nothing, forks nothing and interacts with no one for this project. Never suggest it, in any form: no emails or data requests (Playgroup included), no issues, pull requests, comments or forum posts anywhere, no forks. The project works with what is public and with what its own runs produce; the only pushes are to the owner's own repositories.
- **No upstream filing.** Forge bugs seen in runs are noted in `docs/upstream.md` for our own reference only; this project does not file Forge issues or PRs, so never suggest it.
- **Per-deck bots, not a general bot.** Custom behaviour reaches a seat only through that seat's playbook and data, written for one specific deck (a precon or a deck from the user's meta). Shared behaviour modules are fine, but they stay inert unless a deck's playbook opts in with its own parameters, and seats without a playbook run stock Forge AI, untouched, as the baseline. We are not building a generalised bot: nothing is switched on for every deck regardless of context, and Forge's default AI is not rewritten. Phase 3 data (`playbook/precons/<id>.json`, DESIGN §19) reaches a seat through the harness `--data` and that seat's profile; Forge's role and combo lists are global for a game, so only lines about the deck's own cards go in.
- **Always pass a clock** to sim mode (`-c` / `--clock`). Forge's default is 120 s and declares longer games a draw; Commander games routinely exceed it. The harness also caps turns (`--turn-cap`, default 120).
- **Event schema:** changes to the JSONL events or `run.json` keep `runner/rollup.py` and `DESIGN.md` §6 in sync and bump `VERSION`.
- **License:** this repo is GPL v3 because `controller/` compiles against Forge. Don't vendor non-GPL-compatible code.
- **Naming:** project is "Vibefish". "MTG" / "Magic: The Gathering" appear only descriptively, never in the product name, repo name, or logos.
- **Benchmark pod** in `runner/benchmark-pod.json` is frozen. Do not edit it. The **precon league** in `runner/precon-league.json` (`league-v1`, 91 decks) is frozen too: a different deck list is a new league with a new name. The same goes for the small leagues in `runner/leagues/` (`bots-v1`, the four decks with a shipped playbook on 2026-11-11; `bots-v2`, the twelve of 2026-11-12, which is the pool the exams draw opponents from now): another list is `bots-v3`, a new file.
- **Human references** (`runner/reference/`): figures copied from Playgroup.gg's public pages with the retrieval date, the page and the licence noted (`playgroup-commander.json`, transcribed from one saved copy of the precon tier page by `transcribe-playgroup.py`; `playgroup-cards.json`, twelve cards' play figures read one page a card on 2026-11-11, provisional). Using them is allowed: Playgroup's legal page publishes its aggregated statistics under CC BY 4.0, to be credited with a link to the page, and its robots.txt lets crawlers read the statistics pages (DESIGN §26). Nothing in the pipeline fetches playgroup.gg: that is this project's own caution from the session that first copied the table, not something the site asks for and not a rule the owner set. The figures are context, not a yardstick for a bot (Status, What the human figures are worth): collect no more of them unless the owner asks.

Relative paths given to the launcher resolve against the directory you run it from. The harness jar is built per Forge jar under `controller/out/<jar-name>/`. `controller/build.sh` builds only when it has to (no jar, another Forge jar, a source newer than the jar; `--force` builds regardless) and swaps the new jar in by rename, so a game that is running keeps the jar it started with; games started after a source change run the new code, so do not change `controller/src` while a long run is using that tree. `--mc on|max|lite` switches Forge's Flat Monte Carlo AI on (2.0.16+ builds, no-op on 2.0.15); `--profile` once per seat, `--rotate-profiles` shifts the assignment every game. Bundled Commander precons: `forge/runtime/res/quest/commanderprecons/` (179 decks named `Name [SET] [YEAR].dck`). Forge needs Java 17+ (CI uses Temurin 21). Sim mode does not need card images.

## Forge sim mode notes
Four `-d` decks in plain mode = one 4-player game (confirmed Phase 0). **Never use `-t`/`-p` for Commander:** tournament mode pairs decks 1v1 at 20 life and ignores `-D` for named decks. `-D` must be absolute; quote names with spaces. Per-seat AI profiles: `-a` in sim mode, `--profile` in the harness (`res/ai/*.ai`). Forge's AI prints a `java.util.concurrent.TimeoutException` stack trace when its own decision timeout fires; harmless. Forge's user data is redirected into `forge/runtime/profile/` by the `forge.profile.properties` the fetch script writes.

## Workflows
- `phase0.yml`: Forge sim-mode smoke test on push to `forge/**`, `runner/**`.
- `pod-run.yml` (manual): 4 shards × N games, rollup, optional publish into `demo-data/` on the branch.
- `league-run.yml` (manual, or a push to `testing` that changes `runner/queue/league-run.json`): a league in up to 20 shards (the league file, cycles, seed, Forge channel and snapshot build, profile, Monte Carlo, playbooks as inputs), rollup and scorecard, optional publish of `rollup.json`, `scorecard.json` and `league.json` into `demo-data/` on the branch. Per-game data stays in the run's artifacts. The league file is `runner/precon-league.json` (the 91 precons) unless the request names another: `runner/leagues/bots-v1.json` is the four decks with a shipped playbook as one table, and with `playbooks` every seat is a bot.
- `ab-run.yml` (manual, or by commit): paired A/Bs of per-deck data for a list of decks (tables, arms, shards per deck, `opponents` 1 for duels), one rollup per deck as artifacts; nothing is committed. A deck written `deck@name` plays the candidate playbook `playbook/variants/<deck>-<name>.json`; a candidate run with `arms: playbook` on the seed of an earlier run pairs with that run's stock arm (`ab.py join`). The queue file may hold several requests (`"runs": [{decks, arms, seed, ...}, ...]`, each with its own arms and seed, top-level fields as defaults), played as one workflow run. Runs do not wait for each other (since 2026-11-11; before that a branch ran one at a time with one waiting, and a slow last shard held up everything behind it): each push of the queue file starts its run at once and GitHub's limit on concurrent jobs paces them. A push to `testing` that changes `runner/queue/ab-run.json` (the same fields as the inputs; a new `requested` value re-runs the same request) starts it without a click; promoting to `main` starts nothing. Opponents are the league's decks under stock AI unless the request says otherwise: `pool` (a deck list, `runner/leagues/bots-v2.json`) draws them from the bot decks and `opponent_playbooks` seats each under its shipped playbook, which is the exam since 2026-11-11 (Status, How a bot is judged).
- `forge-archive.yml` (manual, or a push to `testing` that changes `runner/queue/forge-archive.json`): packs the runtime of the snapshot builds named there (from the Actions cache, or upstream while it has them) and attaches each to the release `forge-runtimes` with its checksum; commits nothing. An archive already on the release is kept as it is (published runs are pinned to its checksum); only `"replace": true` overwrites one, and `forge/SHA256SUMS` then needs the new checksum at once.
- Pages: no workflow. The `testing` branch is served as-is; a push there is live within about a minute. Workflows that are `workflow_dispatch`-only (`pod-run.yml`) can only be started once they exist on the default branch.

### How a bot is judged (the owner, 2026-11-11)
Not by beating a table of stock AI. The goal is a pilot that plays its deck as a competent person would; stock opponents do not punish what people punish, and it is hard to play like a person against them, so a result at their table says little about that. From here on a candidate's exam is the paired A/B at tables of bots: the deck under stock AI and under its playbook on the same tables, the three opponents drawn from the decks that have a shipped playbook (`runner/leagues/bots-v2.json` since 2026-11-12, `bots-v1.json` before) and each under it (`ab-run` with `pool` and `opponent_playbooks`; `runner/ab.py --pool ... --opponent-playbooks`). The stock arm stays as the control, the same deck in the same seat: without it there is no saying what the rules did. When a bot ships, the bot league is played again with it (a new list, `bots-v2`, through `league-run`) for the standings among bots. The table above is the old exam, three stock seats; it is the record of how the four were chosen. Two things to keep in mind with the new one: until 2026-11-12 the pool was four decks that all win by attacking, three of them token decks, and every result up to `ab-run` #25 was earned against that table; and `playbook_stats` are summed over every playbook seat of a game (one static map in `PlaybookController`, rule numbers collide), so at a table of bots they say nothing about one seat.

The first league of the four bots (`league-run` #2, 200 games, DESIGN §24; on the dashboard): Token Triumph wins 46.0%, Tricky Terrain 22.0%, Goblin Storm and Hail, Caesar 16.0% each. A table of bots plays 10.3 rounds where the same seats under stock play 13.5. The seats lose holding their answers: Hail, Caesar cast Ruinous Ultimatum from hand in 7 of the 35 games it drew it, Tricky Terrain never cast Oblivion Stone or Curse of the Swine from hand (66 and 55 games drawn) and lost 42 and 39 games holding them; the one rule that names an answer (Tricky Terrain's Beast Within and Pongify) is the one that gets them cast. What is missing is the reactive half. (This paragraph used to set the four rates beside "people's share of this table" and call the bots "not yet the decks people play". The human figures cannot carry that, DESIGN §26: nothing is known about how these four fare against each other in people's hands.)

### What the human figures are worth, and where the bots are going (the owner, 2026-11-11)
The owner had taken the human data for games recorded turn by turn, and on learning what it is called it effectively useless as a measuring stick. Checked, and mostly right (DESIGN §25, §26):
- What we hold is aggregates copied from Playgroup's public pages. No game, no turn, no action; every turn-by-turn log in this project is the sim's own.
- A precon's human win rate is how often people won with that exact list against unknown decks that were on average stronger than a precon (the 92 precons average 21%, not 25%). A typical figure is good to five points either way; over half the spread of the table is sampling noise; a second sample of the table would agree with it at a rank correlation of about 0.45 and a perfect simulator at about 0.66 (the stock league's 0.266 was read against 1). The ends of the table are real, the order of the middle is not.
- So a human win rate does not grade a bot: its rate at our tables is against our opponents, people's is against theirs. The figures were a way to pick decks (the ones stock AI plays furthest below their standing among people) and nothing finer. The table-level figures (rounds, mulligans, first seat) are over every deck people track, not precon tables.
- Playgroup records casts only for games on its own online table, keeps those games private and publishes per-card aggregates (drawn, played, turn of the first cast). `runner/cardplay.py` computes the same from our logs and twelve cards are in `runner/reference/playgroup-cards.json`; they showed nothing about the unplayed answers that the logs had not shown already. The file stays and is not extended.
- The yardstick is built from our own games: the paired control at tables of bots; mistakes that need no human to define, counted in the logs (a loss with a castable answer in hand, mana unspent beside castable cards, permanents never activated, cards drawn and never played; not written yet: lethal not taken, the unblocked attack that killed the seat with blockers at home); and the owner reading games (`runner/hands.py game` prints one seat's game turn by turn).

The owner's direction, the same day: this ends with the custom bots handling every step. Today a playbook answers four of the 108 differently named questions Forge puts to a seat's controller (`declareAttackers`, `chooseSpellAbilityToPlay`, `confirmTrigger`, `mulliganKeepHand`); blocks, targets, modes, what to sacrifice or discard, payments, and everything on another player's turn are stock Forge's. A step taken over stays per deck (a hook in `PlaybookController` that is inert until a deck's playbook names it) and earns its place at the tables like a rule does. The session's proposed order, not yet the owner's: answers (in flight), blocks, targets and modes as an effect resolves, responses on other players' turns, mulligans.

### What the measurements settled
- The deck's own lines are the lever: cast and trigger rules moved four decks by 8 to 12 points. Whom the seat attacks moved nothing by itself (`ab-run` #6), and the blocker-counting `pressure` attack lost to `go_wide` on three decks at tables of stock AI and tied with it on the fourth (Hail, Caesar, 45 wins against 44). At tables of bots `go_wide` lost to Forge's own attack on the pool of four and beat it on the pool of twelve for the three decks that carry answer rules (below), and two of those, Hail, Caesar and Tricky Terrain, attack go-wide again since 2026-11-13; `pressure` stays in the code unused.
- The twelve hold up among each other (`ab-run` #26, DESIGN §28): at tables drawn from the other eleven bots the playbooks win 557 of 2,400 tables and the stock pilots of the same decks 419, nine decks ahead, one level, two a point or two behind; four leads are clear of noise. A deck's figure on one pool says little about the next (Limit Break +11.5 on the pool of four, +2.5 among the twelve; Enduring Enchantments level, then +11.0).
- There is no shortcut to 91 playbooks: a mechanical draft (`runner/playbook.py draft`) gains nothing in goldfish on three decks and under half the hand-written rules' gain on a fourth. Decks are picked by an audit of what stock leaves undone and their lines are written by hand.
- Goldfish (minutes) says whether a seat runs its engine, not what that is worth: two turns of speed bought Goblin Storm eleven points and Quick Draw three and a half. Duels misjudged Tricky Terrain. Forty tables and sixty duels were right that the candidates beat stock and wrong about which candidate is best.
- What a bot is, and is not (DESIGN §23, `runner/losses.py` on the 800 games of `ab-run` #17): its rules make two thirds to four fifths of the seat's spell casts and two fifths of its attack declarations. Everything about the other three players is still Forge's and measures the same as stock: under one spell a game aimed at an opponent, one attacker in six blocked, the same mulligans, and a loss that comes within a turn cycle from one opponent with three castable cards in hand.
- A table of the four bots plays a 39-turn game where the same seats under stock play 54 (20 and 17 games on a session's machine; 9.75 rounds against 13.5 by the scorecard's turns over four, people 8.75). Game length follows the pilots (in Actions since: the bot league's 10.3 rounds, DESIGN §24). - At tables of bots the attack policy was giving back most of what the rules earned (`ab-run` #19 and #23 to #25, DESIGN §27). Thirteen decks played the same rules with `go_wide` and with Forge's own attack on the same 200 tables: not one won fewer tables with Forge's attack, and summed over 2,600 tables the stock pilots won 501, the rules with `go_wide` 567 and with Forge's attack 685. - The attack is not settled (`ab-run` #26, DESIGN §28). On the pool of twelve, with their answer rules, Hail, Caesar, Tricky Terrain and Goblin Storm each won more tables with `go_wide` than with Forge's attack on the same 200 tables: 66 against 45 (exact test 0.0046), 58 against 40 (0.027), 56 against 47 (0.26). The rules and the pool both changed since the pool of four, and the round cannot say which turned it. A deck's best attack depends on its rules and its table: the case for an attack written per deck, against any default.
- Where a table's attention goes is Forge's, and it reads the same at stock tables and among the twelve (`runner/heat.py`, DESIGN §28): 72 to 76% of attackers go at the opponent with the most nonland permanents (chance 40%), 52 to 57% at the lowest life, 52 to 55% at the one opponent who attacked the seat last turn; the player who goes on to win receives 22% (chance 37%). Aimed spells and abilities (3.3 to 3.5 a seat a game, a third to two fifths of them spells) follow the same order more weakly. Forge piles on the widest board and the weakest player; it does not see who is winning. This is the baseline for any judgement of danger written here.
- Answer rules are worth what the seat's position makes them worth (`ab-run` #21, DESIGN §27): wipes that the shipped bots cast in a fifth to two fifths of the games they drew them are cast in three fifths to three quarters under the rules, which gave Hail, Caesar 9.5 points, Goblin Storm 4, Tricky Terrain a lean and Token Triumph, the deck that led that table, nothing.
- So candidates are compared at 200 tables on shared seeds (`deck@variant`, `ab.py join`); a file chosen among several on the same tables gets a confirming run on a seed of its own; local runs are for bugs and for effects of ten points and more.

- One deck's loop: `runner/playbook.py roles` and `draft` for what Forge's scripts say; a dozen stock goldfish games read with `hands.py held`, `abilities` and `game` (and `FORGE_JAVA_OPTS=-Dvibefish.trace=true` on a playbook seat, which prints the optional triggers Forge declines); a candidate in `playbook/variants/`; `goldfish.sh -P` against stock on seeds not looked at before the rules were final (`hands.py compare`); 200 tables through the queue file; then the record: rollups under `demo-data/ab/` and its README, `playbook/variants/README.md`, `playbook/bots.json`, DESIGN, this Status.
- Starting runs: the session's GitHub access cannot dispatch or cancel workflows (403; do not work around it). `runner/queue/ab-run.json` pushed to `testing` starts `ab-run` (`runner/queue/README.md`); the click-only workflows (`pod-run.yml`, `league-run.yml`) need the owner.
- Collecting a run: its status can read `queued` or `in_progress` long after the jobs are done, so go by the artifacts. List them for the run id (GitHub MCP `actions_list`, `list_workflow_run_artifacts`, 100 a page): two per shard, and `ab-rollups` once everything is done, which unzips to `ab-<deck>/rollup.json`. `actions_get` `download_workflow_run_artifact` gives a short-lived URL to curl into the scratch directory. 200 tables of two arms in ten shards take about an hour.
- Seeds: a deck's runs are kept ten seeds apart, because nearby seeds draw the same opponents (`runner/ab.py`, Seeds; `play` warns). Goldfish seed blocks are in `demo-data/goldfish/README.md`.
- Local runs: `ab.py play`, `league.py play` and the launcher rebuild the harness jar when sources are newer (and only then, since 2026-11-11: before that every `ab.py play` rewrote the jar under whatever else was running), so a long run that must not change under way gets a copy of the tree in the scratch directory. A container restart kills background runs; their output directories survive and the same command carries on (finished games are not replayed).
