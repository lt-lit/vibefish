# Vibefish — Claude Code context

Read `DESIGN.md` first. This file is the short version plus hard constraints.

## What this repo is
Commander deck playtesting engine built on Forge's headless `sim` mode. Engine only — decks, playbooks and results live in a separate data repo and are passed in by path. `demo-data/` holds the public pod results the dashboard shows.

## Hard constraints
- **Dashboard:** vanilla JS, no build step, no TypeScript, no frameworks. Must work on GitHub Pages and on a phone browser. It reads only the data contract in `DESIGN.md` §6 (`index.json`, `rollup.json`, `cards/scryfall-cache.json`, and the optional `bots.json`).
- **Images:** never commit card image files. Hotlink `cards.scryfall.io` URLs from the cache only; `small` and `normal` only, never cropped art.
- **Scryfall API:** ≥100 ms between requests to `api.scryfall.com`; set `User-Agent: Vibefish/<version>` in scripts (`runner/scryfall.py` does); leave browser UA alone in page JS. Resolve names in batches via `cards/collection`.
- **Forge:** pinned to the tag in `forge/VERSION` with the checksum in `forge/SHA256SUMS`. Do not float to `latest` or `daily-snapshots` unless `FORGE_CHANNEL=snapshot` is explicitly set; a snapshot build that published runs depend on is pinned exactly with `FORGE_SNAPSHOT_BUILD=<build>` and its checksum recorded in `forge/SHA256SUMS` (the 2026-11-08 and 2026-11-10 builds are). The runtime is downloaded by `forge/fetch-forge.sh` into `forge/runtime/` and is never committed. Forge's `daily-snapshots` release holds one tarball at a time, so a pinned snapshot can be fetched from upstream only until the next snapshot replaces it (checked 2026-11-11 16:16 UTC: the 11-10 tarball was still there, no 11-11 build yet, 11-08 and 11-09 answered 404). Snapshot builds that published runs depend on are therefore archived (decided 2026-11-11): `forge-archive.yml`, started by `runner/queue/forge-archive.json`, packs the assembled runtime and attaches it to this repository's release `forge-runtimes`; `forge/SHA256SUMS` lists the archive (`forge-runtime-snapshot-YYYY-MM-DD.tar.gz`), and `forge/fetch-forge.sh` fetches a pinned `FORGE_SNAPSHOT_BUILD` from there when it is listed. The 11-08 and 11-10 builds are archived. When a new snapshot is first used for a published run, archive it straight away (while upstream still has it or the Actions cache does) and add the checksum it prints. The Actions cache key hashes `forge/VERSION`, `forge/SHA256SUMS` and `forge/fetch-forge.sh`, so editing them makes the next run fetch again: fine for archived builds, fatal for a snapshot that is not archived yet. The archive is for reproducing published runs, not for staying on old builds: keep up with Forge (the 2.0.16 release came out on 2026-11-11 and the pin has not moved yet: Status, Next 7).
- **No Forge fork.** `controller/` compiles against the released Forge jar and uses public hooks (event bus, `PlayerControllerAi`). Patch Forge only if a hook is private, and record it in `DESIGN.md`.
- **No upstream filing.** Forge bugs seen in runs are noted in `docs/upstream.md` for our own reference only; this project does not file Forge issues or PRs, so never suggest it.
- **Per-deck bots, not a general bot.** Custom behaviour reaches a seat only through that seat's playbook and data, written for one specific deck (a precon or a deck from the user's meta). Shared behaviour modules are fine, but they stay inert unless a deck's playbook opts in with its own parameters, and seats without a playbook run stock Forge AI, untouched, as the baseline. We are not building a generalised bot: nothing is switched on for every deck regardless of context, and Forge's default AI is not rewritten. Phase 3 data (`playbook/precons/<id>.json`, DESIGN §19) reaches a seat through the harness `--data` and that seat's profile; Forge's role and combo lists are global for a game, so only lines about the deck's own cards go in.
- **Always pass a clock** to sim mode (`-c` / `--clock`). Forge's default is 120 s and declares longer games a draw; Commander games routinely exceed it. The harness also caps turns (`--turn-cap`, default 120).
- **Event schema:** changes to the JSONL events or `run.json` keep `runner/rollup.py` and `DESIGN.md` §6 in sync and bump `VERSION`.
- **License:** this repo is GPL v3 because `controller/` compiles against Forge. Don't vendor non-GPL-compatible code.
- **Naming:** project is "Vibefish". "MTG" / "Magic: The Gathering" appear only descriptively, never in the product name, repo name, or logos.
- **Benchmark pod** in `runner/benchmark-pod.json` is frozen. Do not edit it. The **precon league** in `runner/precon-league.json` (`league-v1`, 91 decks) is frozen too: a different deck list is a new league with a new name. The same goes for the small leagues in `runner/leagues/` (`bots-v1`, the four decks with a shipped playbook on 2026-11-11): a fifth bot is `bots-v2`, a new file.
- **Human references** (`runner/reference/playgroup-commander.json`) are copied from Playgroup.gg's public pages by hand or from one saved page copy, with the retrieval date and the page's CC BY 4.0 licence noted (`runner/reference/transcribe-playgroup.py` reads a saved page file). Nothing in the pipeline fetches playgroup.gg.

Relative paths given to the launcher resolve against the directory you run it from. The harness jar is built per Forge jar under `controller/out/<jar-name>/`; the launcher rebuilds it when sources are newer, so do not run it against a runtime while a long run is using that runtime (the running JVM reads classes from the jar being overwritten). `--mc on|max|lite` switches Forge's Flat Monte Carlo AI on (2.0.16+ builds, no-op on 2.0.15); `--profile` once per seat, `--rotate-profiles` shifts the assignment every game. Bundled Commander precons: `forge/runtime/res/quest/commanderprecons/` (179 decks named `Name [SET] [YEAR].dck`). Forge needs Java 17+ (CI uses Temurin 21). Sim mode does not need card images.

## Forge sim mode notes
Four `-d` decks in plain mode = one 4-player game (confirmed Phase 0). **Never use `-t`/`-p` for Commander:** tournament mode pairs decks 1v1 at 20 life and ignores `-D` for named decks. `-D` must be absolute; quote names with spaces. Per-seat AI profiles: `-a` in sim mode, `--profile` in the harness (`res/ai/*.ai`). Forge's AI prints a `java.util.concurrent.TimeoutException` stack trace when its own decision timeout fires; harmless. Forge's user data is redirected into `forge/runtime/profile/` by the `forge.profile.properties` the fetch script writes.

## Workflows
- `phase0.yml`: Forge sim-mode smoke test on push to `forge/**`, `runner/**`.
- `pod-run.yml` (manual): 4 shards × N games, rollup, optional publish into `demo-data/` on the branch.
- `league-run.yml` (manual, or a push to `testing` that changes `runner/queue/league-run.json`): a league in up to 20 shards (the league file, cycles, seed, Forge channel and snapshot build, profile, Monte Carlo, playbooks as inputs), rollup and scorecard, optional publish of `rollup.json`, `scorecard.json` and `league.json` into `demo-data/` on the branch. Per-game data stays in the run's artifacts. The league file is `runner/precon-league.json` (the 91 precons) unless the request names another: `runner/leagues/bots-v1.json` is the four decks with a shipped playbook as one table, and with `playbooks` every seat is a bot.
- `ab-run.yml` (manual, or by commit): paired A/Bs of per-deck data for a list of decks (tables, arms, shards per deck, `opponents` 1 for duels), one rollup per deck as artifacts; nothing is committed. A deck written `deck@name` plays the candidate playbook `playbook/variants/<deck>-<name>.json`; a candidate run with `arms: playbook` on the seed of an earlier run pairs with that run's stock arm (`ab.py join`). The queue file may hold several requests (`"runs": [{decks, arms, seed, ...}, ...]`, each with its own arms and seed, top-level fields as defaults), played as one workflow run. Runs do not wait for each other (since 2026-11-11; before that a branch ran one at a time with one waiting, and a slow last shard held up everything behind it): each push of the queue file starts its run at once and GitHub's limit on concurrent jobs paces them. A push to `testing` that changes `runner/queue/ab-run.json` (the same fields as the inputs; a new `requested` value re-runs the same request) starts it without a click; promoting to `main` starts nothing. Opponents are the league's decks under stock AI unless the request says otherwise: `pool` (a deck list, `runner/leagues/bots-v1.json`) draws them from the bot decks and `opponent_playbooks` seats each under its shipped playbook, which is the exam since 2026-11-11 (Status, How a bot is judged).
- `forge-archive.yml` (manual, or a push to `testing` that changes `runner/queue/forge-archive.json`): packs the runtime of the snapshot builds named there (from the Actions cache, or upstream while it has them) and attaches each to the release `forge-runtimes` with its checksum; commits nothing. An archive already on the release is kept as it is (published runs are pinned to its checksum); only `"replace": true` overwrites one, and `forge/SHA256SUMS` then needs the new checksum at once.
- Pages: no workflow. The `testing` branch is served as-is; a push there is live within about a minute. Workflows that are `workflow_dispatch`-only (`pod-run.yml`) can only be started once they exist on the default branch.

### How a bot is judged (the owner, 2026-11-11)
Not by beating a table of stock AI. The goal is a pilot that plays its deck as a competent person would; stock opponents do not punish what people punish, and it is hard to play like a person against them, so a result at their table says little about that. From here on a candidate's exam is the paired A/B at tables of bots: the deck under stock AI and under its playbook on the same tables, the three opponents drawn from the decks that have a shipped playbook (`runner/leagues/bots-v1.json`) and each under it (`ab-run` with `pool` and `opponent_playbooks`; `runner/ab.py --pool ... --opponent-playbooks`). The stock arm stays as the control, the same deck in the same seat: without it there is no saying what the rules did. When a bot ships, the bot league is played again with it (a new list, `bots-v2`, through `league-run`) for the standings among bots against people's ordering of the same decks. The table above is the old exam, three stock seats; it is the record of how the four were chosen. Two things to keep in mind with the new one: the pool is four decks that all win by attacking, three of them token decks, so a candidate is judged against that table until the pool is wider; and `playbook_stats` are summed over every playbook seat of a game (one static map in `PlaybookController`, rule numbers collide), so at a table of bots they say nothing about one seat.

### What the measurements settled
- The deck's own lines are the lever: cast and trigger rules moved four decks by 8 to 12 points. Whom the seat attacks moved nothing by itself (`ab-run` #6), and the blocker-counting `pressure` attack lost to `go_wide` on every deck that played both at the tables; `go_wide` is the default, `pressure` stays in the code unused by any shipped playbook.
- There is no shortcut to 91 playbooks: a mechanical draft (`runner/playbook.py draft`) gains nothing in goldfish on three decks and under half the hand-written rules' gain on a fourth. Decks are picked by an audit of what stock leaves undone and their lines are written by hand.
- Goldfish (minutes) says whether a seat runs its engine, not what that is worth: two turns of speed bought Goblin Storm eleven points and Quick Draw three and a half. Duels misjudged Tricky Terrain. Forty tables and sixty duels were right that the candidates beat stock and wrong about which candidate is best.
- What a bot is, and is not (DESIGN §23, `runner/losses.py` on the 800 games of `ab-run` #17): its rules make two thirds to four fifths of the seat's spell casts and two fifths of its attack declarations. Everything about the other three players is still Forge's and measures the same as stock: under one spell a game aimed at an opponent, one attacker in six blocked, the same mulligans, and a loss that comes within a turn cycle from one opponent with three castable cards in hand.
- A table of the four bots plays a 39-turn game where the same seats under stock play 54 (20 and 17 games on a session's machine; 9.75 rounds against 13.5 by the scorecard's turns over four, people 8.75). Game length follows the pilots. No table with more than one bot has been played in Actions, and no deck's win rate among bots has been measured.
- So candidates are compared at 200 tables on shared seeds (`deck@variant`, `ab.py join`); a file chosen among several on the same tables gets a confirming run on a seed of its own; local runs are for bugs and for effects of ten points and more.
